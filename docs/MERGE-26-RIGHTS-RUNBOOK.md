# Merge 26 rights restriction and minimisation runbook

Status: implementation direction selected by owner; SQL controls tested and applied in development only. This is not a claim of complete erasure, anonymity or blanket legal approval. Use only authorised administrators; do not place request contents, identity evidence or email addresses in the case reference.

## Supported controls

Migration124 introduces an admin-authenticated security-definer RPC with empty search_path and private RLS-protected restriction/action tables. Every call requires a non-admin target, explicit boolean choices and a 3–64-character opaque case reference. The RPC records the acting administrator and server time transactionally. Public clients, ordinary accounts and service-role callers cannot directly read or change the tables or invoke the renamed unrestricted resolver. An authenticated admin may call the RPC; checking only an asserted role from the browser is insufficient.

`set_tester_privacy_restriction(p_tester, p_restricted, p_deidentify, p_case_reference)`

- Restriction only: `true,false` hides the public current rank wherever the shared feedback resolver is used, including developer views. Authorised administrator moderation retains its private identity access. Pending/rejected feedback gating is unchanged. Existing open browser views may retain an already rendered label until refresh; previously copied third-party content cannot be recalled.
- Reviewed reversal: `false,false` restores normal attribution only if minimisation has not been applied. It does not allocate a new number or change rank/XP.
- Minimisation: `true,true` also replaces profile display_name with the neutral status Restricted account, optional account PC specifications and availability waiting preferences. Private stable report ownership, Auth account, XP, historical feedback, usefulness, decisions and moderation audits are preserved. The action table remains restricted. Do not describe retained UUIDs/free text/Auth email as anonymous data. A minimised identity cannot be publicly re-enabled by this RPC.

No endpoint is exposed for self-service erasure and no Auth hard-delete or trigger disable is performed. No existing deletion guard or foreign key was weakened. Accounts with developer/admin responsibilities require separate inventory and handling; administrator targets are refused by this tester-focused operation.

## Exact operator procedure

1. Receive request at support.playtested@gmail.com or existing account request workflow. Assign an opaque case ID, verify identity proportionately and record scope, intake/date, response deadline and responsible operator privately. Do not request passwords, tokens or excessive identity documents. Apply justified interim public attribution restriction promptly using an authenticated admin session and the RPC with `true,false`.
2. Inventory Auth/OAuth/session data, profile/PC fields, submitted feedback and free text, public labels, developer contacts/listings/files, notification records, audit/delivery keys and support/provider records. Record each purpose, necessity, proposed erase/restrict/retain decision and review date. A useful report or FK dependency alone does not justify indefinite identifiable retention.
3. For an account-access restriction, the authorised operator must use the supported Supabase Auth administration workflow to ban the account and prevent renewed sessions. Confirm actual token/session expiry and revocation behaviour; existing access tokens may remain usable until expiry. Verify that sign-in/refresh and a previously issued session can no longer perform protected actions before treating containment as complete. This provider operation was NOT run against production and is NOT implemented by the SQL attribution flag. Do not claim that hiding a badge disables account access.
4. When approved, run `true,true` for the narrow minimisation described above, using the administrator's authenticated server/client RPC context (never embed an admin credential in a browser form). Check RPC success, a refreshed public lookup returning null rank, no private PC fields/waiting preference, unchanged report IDs/ownership/outcomes/XP and a recorded case action. On any failure stop; the transaction must roll back. Repeat only against the same verified target/case after checking prior outcome.
5. Review free-text reports, files, external copies and remaining Auth/profile/contact identifiers individually. Do not rewrite original reports wholesale, recycle ownership into another tester, delete audits or disable submitted-report guards. A request requiring further redaction/erasure needs a reviewed, field-specific audited operation; that is outside this narrow RPC. Do not report those remaining fields erased.
6. Respond with completed actions, justified retained categories/purpose/review dates, unresolved processor/backups handling and the applicable challenge/complaint route. Track the applicable response deadline; assess any lawful extension, refusal or pause explicitly. Restore restrictions to a recovered database before returning restored content to public service; backup retention is not an exemption from rights handling.

## Evidence and remaining scope

`tests/test-merge26-privacy-controls.mjs` executes real migration124 SQL against an isolated PostgreSQL fixture, including the original submitted-report guard. It verifies anonymous/ordinary-user denial, private table/bypass denial, admin-only masking/reversal, validation, non-reversible minimisation, unchanged reports/XP/Auth ownership and continuing rejection of hard deletion/identity recycling. No genuine historical record is altered by these tests.

Full provider account-ban/session-revocation and case-specific free-text/linked developer-data erasure are manual operational verification, NOT passed automated tests. Auth hard deletion remains unsafe for a genuine report owner because tester_id is NOT NULL with Auth CASCADE while report audits/signals and submitted-place guards protect historical records. This procedure offers tested restriction and partial minimisation, not a universal account-erasure button.

Hosted development evidence: a newly created empty disposable account was banned through supported Auth administration; new sign-in and refresh failed, while its existing JWT could still read until expiry. Real-admin restriction/minimisation then passed. Only that newly created empty Auth account was removed; no genuine historical report or audit was deleted. Intended minimal privacy-action audit/tombstones for disposable cases remain private. The fixture has NOT NULL profile names like deployed schema; minimisation uses Restricted account, not NULL.
