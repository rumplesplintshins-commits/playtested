# Shared CPU/GPU catalogue

Source: lib/hardware-catalogue.json; matching/display: lib/hardware-catalogue.ts; shared accessible input: HardwarePicker through PcFields. No runtime provider lookup, hardware detection, performance ordering or compatibility inference. The starter catalogue is intentionally not exhaustive; Other / Not listed supports unusual, integrated, legacy and newly released models.

Recognised models save one stable cpu: or gpu: canonical string ID in the existing cpu/gpu JSON field. Labels are resolved from the same catalogue for Account selectors and public/private requirement displays. A custom choice is stored as custom: plus at most 153 characters (160 total); it is never recognised as a catalogue entry even if its text resembles a known model. Existing unmatched legacy strings retain their exact value until the user edits them. Recognised legacy labels/aliases are canonicalised on an explicit successful save, with no background data rewrite. Clearing remains optional. No table/column migration or bulk rewriting of hardware records is needed; existing SQL length/field/owner-RLS checks apply unchanged.

To add a model: verify its manufacturer/model label from authoritative vendor material; add exactly one row to the correct CPU/GPU list with a unique stable ID and standard label; do not reuse IDs. Check aliases remain unambiguous and CPU/GPU types separate using tests/test-merge26-hardware.mjs. Never merge or silently relabel existing custom entries. Do not attach performance scores or infer compatibility from names. Retired labels should preserve their ID/display mapping for saved records. Run TypeScript, hardware browser/unit tests and focused PC save/privacy tests when changing the catalogue.

The combobox searches manufacturer/series/model, handles arrows/Enter/Escape, shows empty results and an explicit custom path, and keeps options in ordinary document flow with an internal scrolling list. It does not depend on an overlay that can be clipped by cards/modals. Existing optional form/disclosure behaviour is shared across Account, minimum, recommended and listing-edit interfaces.
